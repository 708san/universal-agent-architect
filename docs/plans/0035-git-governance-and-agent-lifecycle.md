# Plan 0035 — Git governance and generated-agent lifecycle

Status: implemented for the documentation and generated-instruction slice

## Objective

Strengthen the Git workflow for this repository and make the same safe, reviewable
development lifecycle explicit in agents generated by Universal Agent Architect.
Keep the change documentation-first, deterministic and offline-compatible.

## Facts

- `docs/DEVELOPMENT_WORKFLOW.md` already defines short-lived branches, Conventional
  Commits, pull requests and explicit approval for history-changing operations.
- Generated project instructions mention branches and approval, but do not describe the
  full latest-main → branch → test → PR → CI/review → merge → cleanup lifecycle.
- GitHub branch protection and required checks are external repository settings and cannot
  be inferred from files in this repository.
- The generated agents are instruction/configuration artifacts; they do not themselves
  provide a Git hosting service or guarantee runtime enforcement.

## Scope

1. Expand repository Git workflow documentation with branch entry/exit checks, PR gates,
   merge cleanup, release/hotfix handling and GitHub settings verification.
2. Add the same default lifecycle to `docs/AGENT_DEVELOPMENT_STANDARD.md` for generated
   agents and Skills.
3. Centralize the generated Git workflow text so Codex, Claude Code, Gemini CLI and
   Antigravity outputs do not drift; include a concise equivalent in the ChatGPT Skill.
4. Add tests that verify every supported generated target contains the workflow and does
   not weaken the approval/destructive-operation guard.
5. Update the PR template and start prompt so human contributors and Codex sessions use
   the same checklist.

## Out of scope

- Changing GitHub repository settings through an API.
- Automatically committing, pushing, merging or deleting branches.
- Adding a GitHub CLI dependency, hosted service, telemetry or network behavior to UAA.
- Claiming that generated instructions enforce permissions in a target runtime.

## Risks and controls

- Generated text could imply a target runtime enforces Git permissions. Keep the text
  advisory and preserve explicit unsupported/runtime-enforcement limitations.
- A duplicated template could drift across adapters. Use one pure shared renderer and
  test all target outputs.
- Stronger PR gates could conflict with emergency fixes. Document a narrowly scoped hotfix
  path with post-incident review, without weakening no-force-push and no-secret rules.
- Documentation could imply branch protection exists. Label GitHub settings as an external
  verification step.

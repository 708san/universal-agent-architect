# Release readiness standard

This document defines when Universal Agent Architect, or an agent generated by it, may be described
as production-ready. A passing structural schema check is necessary but never sufficient: generated
instructions do not provide a runtime sandbox or grant permissions.

## Decision states

- **Ready** — every applicable gate has evidence, and unsupported capabilities are not being claimed.
- **Conditional** — the scope is explicitly limited (for example, offline Codex staging only), with
  known limitations documented in the release notes.
- **Blocked** — any security, data-flow, compatibility or rollback gate is missing or failing.

## Gates for this repository

### Functionality

- [ ] `npm run check` passes offline on a clean checkout.
- [ ] The Blueprint conforms to `schemas/blueprint-0.1.schema.json`.
- [ ] Identical safe inputs produce identical facts, Blueprint and validation results.
- [ ] Unsupported targets fail visibly and do not receive fabricated adapter files.
- [ ] Generated output uses relative safe paths, is staged, and cannot silently overwrite source files.
- [ ] Browser and CLI inventory behavior has convergence fixtures.

### Security and privacy

- [ ] Traversal, absolute paths, symlink escape and sensitive-path fixtures pass.
- [ ] Oversized and malformed manifests fail closed without retaining their contents.
- [ ] Hostile project instructions, malicious Skills and prompt-injection text are treated as data.
- [ ] No network, telemetry, cloud-model call or third-party MCP start occurs by default.
- [ ] Writes, process execution, MCP calls and external disclosure have explicit approval gates.
- [ ] Reports and logs contain no credentials or raw private source; filename disclosure is documented.
- [ ] Strict-profile checks cover tool misuse, MCP redaction and resource limits.
- [ ] Any claimed runtime isolation is tested outside the declarative Blueprint; schema validation alone
  is not evidence of enforcement.

### Operations

- [ ] Every supported workflow has bounded time, file, recursion, retry and cost behavior where relevant.
- [ ] Failures are visible, actionable and do not leave partial writes or ambiguous output ownership.
- [ ] Apply, rollback and recovery procedures are documented before enabling project mutation.
- [ ] Dependency changes are reviewed with a lockfile and a reproducible CI install.
- [ ] Security contact, private vulnerability reporting and incident response ownership are defined.
- [ ] Release artifacts identify the source revision, schema version, capability-registry version and
  verification results.

### Compatibility

- [ ] Each target adapter names its target/version/edition and cites an official specification source.
- [ ] Positive, negative and unsupported fixtures exist for every declared target capability.
- [ ] Features that cannot be verified are marked `unknown` or `unsupported`, never silently rendered.
- [ ] Generated Skills pass frontmatter and target-specific validation.

## Current assessment

The repository is **Conditional** for the offline Codex prototype. The pure core, bounded inventory,
security profiles, generated safety instructions and offline tests are present. It is **not** ready to
claim production-grade project protection because runtime sandboxing, full adapter verification,
browser end-to-end boundary tests, formal schema validation in the application, MCP authorization and
operational rollback are still incomplete.

## Generated-agent minimum

A generated agent may be used for a production project only when its target adapter has verified:

1. the target and version/edition;
2. its actual tool and filesystem permission behavior;
3. network and external-data approval behavior;
4. positive, negative and security test evidence;
5. failure, rollback and incident-reporting procedures.

The `baseline` and `strict` profiles in the Blueprint are requirements and test plans. They are not
proof that a host runtime enforces those requirements.
